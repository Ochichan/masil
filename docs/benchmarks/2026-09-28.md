# 2026-09-28 설치된 Herdr와 코어 비교

실제 실행한 초기 비교다. masil은 stock tmux에 가까운 코어 비용을 유지했고, 이 조건에서 Herdr보다 적은 RSS와 짧은 입력 왕복 시간을 보였다. Herdr는 단일 pane 출력 CPU와 1 MiB burst의 PTY 쓰기 완료 시간에서 앞섰다. 전체 제품 기능이 같은 비교나 언어 자체의 성능 비교는 아니다.

[원시 JSON](data/2026-09-28-comparison.json), [build·binary·측정 코드 hash](data/2026-09-28-provenance.json), [측정 도구](../../tests/performance/README.md)를 함께 보존한다. 세 제품의 모든 조건이 measured로 완료됐으며 모든 inner grid 비교가 일치했다.

## 실행 조건

- 2026-09-28 09:33:31~09:45:35 KST. macOS arm64, Mac17,9, RAM 64 GiB, 논리 CPU 18개.
- masil과 stock은 tmux commit `94796f6b1182507efac8a272fc309a79e22e58a5`, Apple clang 21, 같은 `-O2`/utf8proc/jemalloc build다.
- Herdr는 사용자 컴퓨터에 설치돼 있던 **0.8.2, API protocol 20**이다. 조사에 사용한 0.9.1 clone이나 최신판의 결과로 확대하지 않는다.
- masil 관찰 bridge는 off이고 Rust CLI/agentd는 실행하지 않았다. 실제 AI provider, 네트워크 모델 요청도 없다.
- 같은 Python raw/noecho PTY fixture를 사용한다. 1·15·50개 pane을 각각 독립 window/tab에 배치했다. 동시에 보이는 50개 split은 아니다.
- host PTY는 120×40, active inner pane은 93×39, hidden pane은 94×39. 실제 child가 보고한 값을 모두 검증했다.
- 제품별 시작 100회, attached RTT 100회, 각 pane 수의 headless idle 10초, 각 출력 조건 1회. paced 출력은 조건별 60초다.
- 전체 출력률은 pane 수와 관계없이 약 1 MiB/s다. 각 pane에 균등 분배하며 정수 나눗셈 때문에 실제 총량이 몇 byte 줄어든다.
- 출력은 CUP + ASCII 80글자 + EL로 같은 위치를 갱신한다. scrollback 기본값이 달라 계속 scroll하는 부하를 본 비교에서 사용하지 않았다.
- private HOME/XDG/config/socket을 사용하고 Herdr의 onboarding·sound·update check·experimental pane history를 껐다. 사용자 session/config는 사용하지 않았다.

본 측정에서는 빌드·테스트를 병행하지 않았다. 일반 host background activity는 그대로였고 masil, stock, Herdr 순서로 한 번씩 실행했다. CPU affinity, cold cache, thermal state를 통제하지 않았다.

## 시작과 입력 왕복

단위 ms. 시작은 중앙값 / P95, RTT는 중앙값 / P95 / P99다.

| 측정 | masil | stock tmux | Herdr 0.8.2 |
| --- | ---: | ---: | ---: |
| 서버 접속 가능 | 11.97 / 13.79 | 12.89 / 15.06 | 7.49 / 38.42 |
| session/workspace 생성 CLI 완료 | 11.97 / 13.79 | 12.89 / 15.06 | 24.98 / 47.42 |
| fixture child 준비 완료 | 35.09 / 38.00 | 36.92 / 43.86 | 63.72 / 87.06 |
| 입력 → host 화면 응답 | 2.67 / 2.87 / 3.52 | 2.65 / 2.87 / 3.04 | 16.68 / 17.84 / 22.23 |

서버 접속 가능의 끝점은 제품마다 다르다. tmux는 detached new-session이 반환되는 시점이며 Herdr는 private server status가 running인 시점이다. Herdr가 이 단계에서 먼저 응답해도 workspace와 child는 아직 준비되지 않았다. child 준비 시간에는 제품별 pane 실행 CLI 절차와 Python 초기화가 포함된다. 순수 process spawn 또는 executable load 시간으로 해석하지 않는다.

입력은 실제 attach client의 PTY에 쓰고, child의 unique 응답이 host 화면에 나타날 때 끝난다. Herdr의 differential redraw 때문에 raw stream의 substring만 찾지 않고 pyte 0.8.2로 화면을 복원했다. 수신 시각은 응답을 완성하는 read 직후, parser·log 처리 전에 기록한다. 물리 모니터에 그려지는 시각은 측정하지 않았다.

## 대기 중 메모리와 CPU

headless **서버만** 계측한다. RSS는 interval 끝의 MiB, CPU는 한 논리 core를 100%로 한 평균이다. Python child와 benchmark process는 표에서 제외한다.

| Pane 수 | masil RSS / CPU | stock RSS / CPU | Herdr RSS / CPU |
| ---: | ---: | ---: | ---: |
| 1 | 4.00 MiB / 0.00% | 3.94 MiB / 0.00% | 20.77 MiB / 0.10% |
| 15 | 4.20 MiB / 0.00% | 4.09 MiB / 0.00% | 28.17 MiB / 0.49% |
| 50 | 4.44 MiB / 0.00% | 4.39 MiB / 0.00% | 48.61 MiB / 1.98% |

0.00%는 `ps` CPU 누적 시간의 0.01초 분해능에서 10초 동안 증가가 관측되지 않았다는 뜻이다. 정확히 CPU를 전혀 쓰지 않는다는 주장도, 10분 idle gate 통과도 아니다. RSS는 macOS physical footprint/PSS와 다르며 공유 page를 합산하면 중복 계수할 수 있다.

참고로 1-pane attached RTT 직후의 server/client RSS는 다음과 같다. 같은 시점의 snapshot이며 peak가 아니다.

| 프로세스 | masil | stock tmux | Herdr 0.8.2 |
| --- | ---: | ---: | ---: |
| 서버 | 4.91 MiB | 4.84 MiB | 21.55 MiB |
| attached client | 5.23 MiB | 5.17 MiB | 12.02 MiB |

## 60초 출력 부하

약 60 MiB를 조건별로 입력했다. 모든 fixture의 offered/completed byte가 일치했다. 50-pane 조건의 실제 총량은 62,913,000 byte다. 아래는 headless server의 RSS / 평균 CPU다.

| Pane 수 | masil | stock tmux | Herdr 0.8.2 |
| ---: | ---: | ---: | ---: |
| 1 | 4.00 MiB / 3.16% | 3.92 MiB / 3.01% | 20.91 MiB / 1.87% |
| 15 | 4.22 MiB / 2.00% | 4.12 MiB / 2.53% | 28.53 MiB / 3.14% |
| 50 | 4.81 MiB / 2.28% | 4.70 MiB / 2.55% | 47.97 MiB / 6.56% |

masil의 50-pane 평균 CPU는 2.28%, Herdr는 6.56%였다. 단일 pane에서는 masil 3.16%, Herdr 1.87%로 순서가 바뀐다. 이 한 번의 실행으로 parser, scheduler, rendering 또는 allocator 중 어떤 요소가 원인인지 판정하지 않는다.

출력량은 fixture의 모든 PTY write가 반환됐다는 sidechannel로 확인했다. kernel/PTY queue를 완전히 처리했거나 표시했다는 증거는 아니다. CPU 표는 출력 시작 전부터 write 완료 후 grace까지 포함하며 대략 60.8초 구간이다. 계속 scroll하는 로그, 복잡한 색/Unicode, 실제 TUI의 화면 변경 패턴은 추가 workload가 필요하다.

## 짧은 burst

약 1 MiB를 한꺼번에 쓰는 조건에서 첫 write부터 마지막 write 반환까지의 ms다. 1회 측정이므로 최대 지속 처리량 수치로 사용하지 않는다.

| Pane 수 | masil | stock tmux | Herdr 0.8.2 |
| ---: | ---: | ---: | ---: |
| 1 | 15.42 | 17.19 | 7.91 |
| 15 | 16.24 | 15.72 | 8.86 |
| 50 | 16.41 | 16.63 | 9.02 |

Herdr가 이 조건에서는 먼저 write를 완료했다. 작은 burst에서는 PTY buffering과 wakeup 방식의 영향도 있으므로 화면 처리 throughput이 두 배라는 결론은 내리지 않는다.

## 해석과 다음 검증

현재 코어에 추가한 변경은 agent-off 경로에서 stock tmux와 비슷한 비용을 보였다. masil의 입력 중앙값 차이는 stock 대비 약 0.013 ms이고, 50-pane idle RSS 차이는 48 KiB였다. 실행 순서가 고정된 단일 실험이므로 작은 차이의 개선/회귀를 확정하지 않는다.

Herdr 대비 낮은 메모리는 현재 terminal core의 장점이다. Herdr는 workspace·상태·원격 등 더 많은 기능을 포함하는 제품이고 masil의 agent 관리 계층은 아직 없다. 이 표를 완성된 masil의 자원 예산으로 사용하거나 C와 Rust의 우열로 바꾸면 안 된다.

artifact의 `budget_eligible=false`, `performance_budget_pass=null`을 유지한다. 설계의 full gate는 10분 idle, RTT 1,000회 이상, 60초 출력 3회 반복 및 추가 관찰/provider 조건을 요구한다. 이번 초기 비교는 그 gate를 통과한 결과가 아니다.

다음 성능 작업은 bridge-on과 느린 reader 부하, 반복·순서 교차 측정, 실제 agent TUI의 UTF-8/scrolling/split redraw fixture다. 단일 pane 출력의 tmux 비용은 sampling profiler로 원인을 확인한 뒤 변경해야 한다.

## 재현

```sh
make core baseline benchmark-env
.build/bench-venv/bin/python tests/performance/benchmark.py \
  --profile smoke --products masil,tmux-baseline,herdr-0.8.2 \
  --pane-counts 1,15,50 \
  --inner-columns 93 --hidden-inner-columns 94 --inner-rows 39 \
  --startup-samples 100 --rtt-samples 100 --idle-seconds 10 \
  --throughput-seconds 60 --throughput-repeats 1 \
  --aggregate-rate-bytes-per-second 1048576 --output-style inplace \
  --output .build/comparison-rerun.json
```

측정 tool은 Herdr 0.8.2와 protocol 20을 확인하고, 실제 geometry가 다르면 실패한다. 다른 버전/환경을 비교하려면 adapter와 조건을 먼저 검증하고 새 artifact로 보존한다. 기존 측정 파일을 덮어쓰지 않는다.
